# نطاق الـ MVP — Watesly Travel AI

## 1. هدف الـ MVP

إطلاق نسخة تشغيلية أولى تُثبت دورة مبيعات سفر كاملة عبر واتساب ولوحة التحكم، لمؤسسة واحدة أو عدة مؤسسات تجريبية، مع:

- فهم طلب السفر واستكمال البيانات
- بحث عبر مزود تجريبي واضح (+ جاهزية Adapter لمزود حقيقي لاحقًا)
- تسعير داخلي بالتكلفة/البيع/الربح
- إرسال عرض سعر للعميل بسعر البيع فقط
- إعادة تحقق قبل الحجز
- تحويل بشري
- عزل Multi-Tenant أساسي

---

## 2. مبادئ تحديد النطاق

- نبني **شريطًا رأسيًا كاملًا** (End-to-End) وليس كل الوحدات بعمق كامل.
- نفضّل الصحة التشغيلية والضوابط على كثرة الميزات.
- لا أسعار مخترعة.
- لا اعتماد على مزود سفر واحد في التصميم حتى لو تأخر الربط الحقيقي.

---

## 3. داخل نطاق الـ MVP (Must Have)

### 3.1 المنصة والحسابات
- تسجيل مؤسسة (Organization)
- مستخدمون داخل المؤسسة
- أدوار أساسية: `Owner`, `Admin`, `Agent`, `Viewer`
- صلاحيات حساسة للعمليات الحرجة
- عزل البيانات بـ `organizationId`

### 3.2 واتساب
- ربط حساب واتساب Cloud API لكل مؤسسة (إعداد يدوي عبر متغيرات/لوحة)
- استقبال الرسائل الواردة (Webhook)
- إرسال رسائل نصية وقوالب أساسية
- عرض المحادثات في اللوحة
- حالة محادثة: `bot`, `human`, `closed`

### 3.3 العملاء والمحادثات
- إنشاء/تحديث Contact من رقم واتساب
- سجل رسائل واردة/صادرة
- ربط المحادثة باستعلام سفر
- بحث بسيط عن العملاء والمحادثات

### 3.4 الاستعلامات المباشرة
- إنشاء استعلام سفر يدويًا من اللوحة (بدون واتساب)
- نفس نموذج بيانات الرحلة المستخدم مع المحادثات

### 3.5 الذكاء الاصطناعي (فهم فقط)
- استخراج:
  - مدينة المغادرة
  - الوجهة
  - تاريخ الذهاب/العودة
  - البالغين/الأطفال/الرضع
  - درجة السفر
  - الميزانية
  - التفضيلات النصية
- اكتشاف الحقول الناقصة وسبرها بسؤال واحد واضح في كل مرة
- **منع تام** لتوليد الأسعار أو التوافر

### 3.6 البحث والسفر
- دعم أولي مركّز على:
  - بحث الطيران (دولي كمسار أساسي)
  - هيكل جاهز للفنادق (واجهة Adapter حتى لو تنفيذ جزئي/تجريبي)
- Mock Travel Provider كامل وواضح في الاستجابات
- تسجيل مصدر كل عرض (`providerId`, `providerOfferRef`)

### 3.7 التسعير والعروض
- قواعد تسعير أساسية لكل مؤسسة:
  - نسبة مئوية
  - مبلغ ثابت
  - حد أدنى للربح (اختياري في MVP)
- إنشاء Quote داخلي يحتوي تكلفة/بيع/ربح
- إرسال عرض للعميل يتضمن سعر البيع وتفاصيل الرحلة فقط
- صلاحية زمنية للعرض (`expiresAt`)

### 3.8 إعادة التحقق والحجز
- عند قبول العميل أو طلب التأكيد: إعادة تحقق من السعر/التوافر
- إذا تغيّر السعر: إبلاغ العميل/الموظف حسب السياسة
- إنشاء Booking Request ثم Booking بحالة واضحة
- لا إصدار نهائي بدون صلاحية مناسبة

### 3.9 التحويل البشري
- زر/أمر تحويل من الآلة إلى موظف
- إشعار داخل اللوحة
- احتفاظ بملخص الطلب والسياق
- إمكانية إعادة للمحادثة الآلية لاحقًا (سياسة بسيطة)

### 3.10 اللوحة العربية (شاشات MVP)
1. لوحة التحكم (مؤشرات أساسية)
2. الاستعلامات المباشرة
3. المحادثات
4. العملاء
5. عروض الأسعار
6. الحجوزات
7. مزودو السفر (تفعيل/إيقاف + إعدادات أساسية)
8. قواعد التسعير والأرباح
9. الموظفون والصلاحيات
10. الإعدادات

> الحملات والتقارير المتقدمة يمكن أن تكون Minimal أو مؤجلة جزئيًا حسب القرار.

### 3.11 الأمن والتدقيق
- مصادقة للوحة
- فرض الصلاحيات في API
- Audit Log للعمليات الحساسة:
  - تعديل قواعد التسعير
  - إرسال عرض
  - إعادة تحقق
  - إنشاء حجز/إصدار
  - تحويل بشري
  - إدارة مزودين

---

## 4. داخل النطاق بشكل مبسّط (Should Have خفيف)

- حملات واتساب بسيطة (قائمة عملاء + قالب + جدولة أساسية)
- تقارير أولية:
  - عدد المحادثات
  - عدد العروض
  - عدد الحجوزات
  - إجمالي المبيعات التقديرية (بسعر البيع)
- إعدادات وكيل الذكاء الاصطناعي (لغة الرد، نبرة مختصرة)
- تأمين سفر / سيارات / توصيل: **عقود وبيانات فقط** أو Mock محدود دون تدفق كامل

---

## 5. خارج نطاق الـ MVP (Won't Have الآن)

- تطبيق جوال أصلي
- اعتماد كامل على مزودين متعددين حقيقيين في الإنتاج
- محرك تسعير ديناميكي معقّد (حسب المنافس/الموسم/الأرباح التصاعدية)
- بوابة دفع متكاملة متعددة الدول (يمكن تسجيل حالة الدفع فقط)
- محاسبة كاملة أو فوترة ضريبية متقدمة
- سوق إضافات (Marketplace)
- تعدد اللغات الكامل للوحة (الإنجليزية لاحقًا؛ العربية أولًا)
- ذكاء اصطناعي صوتي
- برنامج ولاء العملاء
- تكامل CRM خارجي
- White-label كامل النطاق
- عمليات حذف جماعي خطرة أو أدوات Platform Admin المتقدمة جدًا

---

## 6. معايير قبول الـ MVP

يُعتبر الـ MVP ناجحًا إذا أمكن لمؤسسة تجريبية أن:

1. تربط واتساب وتستقبل رسالة عميل.
2. يستخرج النظام بيانات الرحلة ويسأل عن الناقص.
3. يبحث عبر Mock Provider (أو مزود حقيقي إن جُهّز).
4. يطبّق قاعدة ربح وينشئ عرضًا.
5. يرسل للعميل سعر البيع فقط.
6. يعيد التحقق عند الموافقة.
7. ينشئ طلب حجز/حجز بحالات واضحة.
8. يحوّل المحادثة لموظف مع السياق.
9. لا يمكن لمستخدم بدون صلاحية تنفيذ إصدار حساس.
10. لا تتسرب بيانات مؤسسة إلى أخرى.

---

## 7. فرضيات الـ MVP

- العميل يتواصل عبر واتساب كنقطة أولى.
- العملة الأساسية قابلة للتكوين لكل مؤسسة (مثل SAR) مع عدم دعم تحويل عملات متقدم في البداية.
- فريق المبيعات صغير إلى متوسط لكل مستأجر.
- البحث الأولي للطيران كافٍ لإثبات القيمة قبل توسيع بقية الخدمات.

---

## 8. مخاطر نطاق يجب مراقبتها

| الخطر | التخفيف |
|---|---|
| توسيع كل خدمات السفر دفعة واحدة | تثبيت الطيران أولًا + عقود لبقية الخدمات |
| تعقيد الحملات | حملة بسيطة أو تأجيلها بعد المسار الأساسي |
| دمج دفع حقيقي مبكرًا | تسجيل حالة الدفع + صلاحيات، والبوابة لاحقًا |
| اعتماد مبكر على مزود واحد | Mock + Adapter contract إلزاميان قبل أي دمج |

---

## 9. مخرجات تقنية متوقعة بعد الموافقة على الـ MVP

> ليست جزءًا من مرحلة الوثائق الحالية.

- سقالة Monorepo (Turborepo + TS)
- تطبيقات web/api/worker فارغة قابلة للتشغيل
- Prisma schema أولي مطابق لـ `DATABASE_ENTITIES.md`
- Mock Provider
- وثائق OpenAPI أولية
