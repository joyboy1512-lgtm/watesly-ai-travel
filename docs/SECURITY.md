# الأمن والصلاحيات — Watesly Travel AI

## 1. أهداف الأمن

1. عزل صارم لبيانات كل مؤسسة (`organizationId`).
2. منع تسريب أسعار التكلفة وهوامش الربح للعميل أو لمستخدم غير مخوّل.
3. منع الذكاء الاصطناعي من اختراع أسعار أو تنفيذ حجوزات.
4. حماية العمليات الحساسة (إصدار، دفع، تجاوز تسعير) بضوابط صلاحيات وموافقات.
5. حماية تكاملات واتساب ومزودي السفر والذكاء الاصطناعي.
6. قابلية التدقيق الكامل للعمليات الحرجة.

---

## 2. نموذج التهديدات (مختصر)

| التهديد | مثال | التخفيف |
|---|---|---|
| تسريب بين المستأجرين | تعديل `organizationId` في الطلب | تجاهل أي Tenant ID من العميل؛ الاعتماد على الجلسة |
| تصعيد صلاحيات | Agent يصدر تذكرة | RBAC + فحوصات على مستوى الـ API |
| اختراع سعر | نموذج AI يهلوس رقمًا | فصل AI عن Pricing؛ الأسعار من Adapter فقط |
| إعادة تشغيل Webhook | تكرار رسالة واتساب | تحقق توقيع + Idempotency |
| تسريب أسرار | رفع `.env` | `.gitignore` + `.env.example` فقط + أسرار خارج المستودع |
| حجز بسعر منتهٍ | قبول عرض قديم | إعادة تحقق إلزامية قبل التأكيد |
| Insider misuse | تعديل قاعدة ربح بصمت | Audit Log + صلاحيات `pricing.manage` |

## 3. عزل Multi-Tenant

### قواعد إلزامية
- كل سجل تشغيلي يحتوي `organizationId`.
- سياق المؤسسة يُستخرج من الهوية المصادقة (Membership)، لا من Body حر.
- كل Query يجب أن يفلتر بالمؤسسة الحالية.
- مفاتيح Redis/Queue تتضمن `organizationId`.
- الملفات المؤقتة والصادرات تُقيَّد بالمؤسسة.
- اختبارات آلية لاحقة تثبت عدم القراءة/الكتابة عبر المستأجرين.

### أدوار المنصة
- `Platform Admin` منفصل عن أدوار المؤسسة، ويُستخدم فقط لعمليات تشغيل SaaS.
- لا يستخدم موظفو المؤسسات مسارات Platform.

---

## 4. المصادقة

### لوحة التحكم
- مصادقة مستخدم (بريد/كلمة مرور في البداية).
- كلمات المرور تُخزَّن بهش قوي (مثل Argon2/Bcrypt).
- جلسات آمنة أو JWT قصيرة العمر مع Refresh مُدار بحذر.
- إبطال الجلسات عند تعطيل المستخدم أو سحب العضوية.
- MFA كمرحلة لاحقة موصى بها للـ Owner/Admin.

### تكاملات الخادم
- Webhooks واتساب: تحقق توقيع Meta.
- استدعاءات Worker الداخلية: عبر طوابير موثوقة وليس عبر منافذ عامة بدون مصادقة.
- مفاتيح مزودي السفر/AI: لكل مؤسسة أو للمنصة حسب النموذج المعتمد، مع تشفير at-rest.

## 5. التفويض (RBAC)

### أدوار MVP مقترحة

| الدور | الوصف |
|---|---|
| Owner | كامل الصلاحيات داخل المؤسسة |
| Admin | إدارة تشغيلية بدون بعض صلاحيات الفوترة إن لزم |
| Agent | محادثات، عروض، حجوزات ضمن حدود |
| Viewer | قراءة فقط |

### صلاحيات حساسة (تتطلب منحًا صريحًا)

| الصلاحية | الاستخدام |
|---|---|
| `pricing.manage` | إنشاء/تعديل قواعد الربح |
| `pricing.override` | تجاوز السعر المحسوب يدويًا |
| `pricing.view_cost` | رؤية التكلفة/الربح داخليًا |
| `quotes.send` | إرسال عرض للعميل |
| `bookings.create` | إنشاء طلب حجز |
| `bookings.issue` | تأكيد/إصدار حجز نهائي |
| `payments.manage` | تسجيل/تعديل حالة الدفع |
| `providers.manage` | إدارة مزودي السفر وأسرارهم |
| `users.manage` | دعوة/تعطيل المستخدمين |
| `whatsapp.manage` | إعداد حساب واتساب |
| `campaigns.manage` | إنشاء وتشغيل الحملات |
| `audit.read` | قراءة سجل التدقيق |

### قواعد أعمال أمنية
- المستخدم بدون `pricing.view_cost` يرى سعر البيع فقط في الواجهة.
- إرسال واتساب للعميل يستخدم `customerVisiblePayload` فقط.
- `bookings.issue` و`payments.manage` يمكن ربطهما بموافقة ثانية (Four-eyes) في المؤسسات التي تفعّل ذلك.
- أي Override سعري يُسجَّل في AuditLog مع السبب.

## 6. سياسة الأسعار والتسعير

1. المصدر الوحيد للتكلفة: Adapter مزود حقيقي أو Mock معلن.
2. المصدر الوحيد لسعر البيع المعتمد: `pricing-engine` + قواعد المؤسسة (أو Override مخوّل).
3. AI قد يذكر ميزانية العميل، لكنه **لا يولّد** سعر عرض.
4. الحقول `costAmount` و`profitAmount` و`pricingBreakdown` داخلية.
5. قبل تأكيد الحجز: `revalidate` إلزامي.
6. إذا تغيّر السعر بعد إعادة التحقق: لا يُصدر الحجز تلقائيًا؛ يلزم قبول جديد أو تدخل مخوّل.

---

## 7. أمن واتساب

- التحقق من Webhook challenge وsignature.
- عدم تسجيل payloads كاملة تحتوي أسرارًا في اللوجات العامة.
- احترام نافذة الـ 24 ساعة وقواعد القوالب.
- معدل إرسال الحملات مضبوط لتجنب الحظر وإرهاق النظام.
- عزل إعدادات كل رقم واتساب بمؤسسته.

---

## 8. أمن مزودي السفر والذكاء الاصطناعي

- كل مزود عبر Adapter؛ لا مفاتيح ثابتة في الكود.
- التمييز الواضح بين بيئة Mock وبيئة حقيقية.
- Timeout + Retry محدود + Circuit breaker لاحقًا.
- لا تُرسل للمزودين بيانات غير لازمة.
- تنقيح سجلات AI من أسرار وتوكنات.
- سياسات احتفاظ لسجلات الاستخراج.

---

## 9. حماية واجهة API

- HTTPS إلزامي في البيئات المنشورة.
- CORS مقيّد لنطاقات لوحة التحكم.
- Rate limiting حسب المستخدم/المؤسسة/IP.
- التحقق من المدخلات (DTO/Schema validation).
- أخطاء عامة للعميل دون تسريب تفاصيل داخلية.
- `requestId` لكل طلب للتتبع.
- منع Mass Assignment على الحقول الحساسة (`organizationId`, `totalCostAmount`, ...).

## 11. التدقيق والمراقبة

### يجب تدقيقه دائمًا
- دخول فاشل/ناجح حسّاس
- تغيير أدوار وصلاحيات
- تعديل قواعد التسعير
- Override للأسعار
- إرسال عروض
- إعادة التحقق ونتائجها
- إنشاء/إصدار/إلغاء حجوزات
- تغيير حالات الدفع
- إدارة مزودين وواتساب
- تصدير بيانات (لاحقًا)

### مبادئ السجلات
- لا كلمات مرور أو توكنات في السجلات.
- ربط الحدث بـ `actorUserId` و`organizationId`.
- الاحتفاظ بـ before/after للحقول الحساسة عند التعديل.

## 12. الخصوصية وتقليل البيانات

- جمع الحد الأدنى من بيانات الركاب للحجز.
- إخفاء جزئي لأرقام الهواتف في الواجهات غير الضرورية لاحقًا.
- سياسات حذف/تصدير بيانات المؤسسة تُعرَّف قبل الإطلاق التجاري.
- فصل بيانات العميل النهائي عن بيانات تكلفة المورد في أي API موجّه للعميل (حتى لو عبر واتساب).
